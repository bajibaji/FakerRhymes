# 韵脚查询逻辑技术文档

本文档详细说明了 FakerRhymes 项目中的韵脚查询核心逻辑。该系统运行于前端，通过预加载优化后的字典数据到内存中，实现毫秒级的韵脚匹配与查询。

## 1. 核心架构概述

查询系统不依赖后端 API（AI 模式除外），而是基于**前端内存字典**。核心流程如下：

1.  **数据加载**：将分割的 JSON 字典文件加载到内存。
2.  **预处理**：将汉字转为“韵母编码+声调”的键 (Key)。
3.  **查询**：将用户输入转为同样的键，根据宽松度生成变体键，在 Map 中查找。

## 2. 数据结构

### 2.1 字典存储 (`globalDictData`)
系统维护一个全局 `Map`，结构为：
- **Key**: 编码后的韵律特征字符串（如 `h192`）。
- **Value**: 对应的词语数组（如 `["黑暗", "河岸"]`）。

### 2.2 键编码规则 (`encodeKey`)
为了压缩内存占用并统一格式，韵母被映射为单字符代码。

**映射表 (`finalToCode`):**
| 韵母 | 代码 | 韵母 | 代码 | 韵母 | 代码 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| iong | 0 | ang | 9 | ia | m |
| uang | 1 | eng | a | ua | n |
| iang | 2 | ing | b | uo | o |
| ... | ... | ... | ... | ... | ... |

**编码示例:**
- **词语**: "光明" (guang1 ming2)
- **韵母**: `uang`, `ing`
- **代码**: `1`, `b`
- **最终 Key**: `11_b2` (编码+声调) -> `11b2` (去下划线)

### 2.3 后缀索引 (`suffixIndex`)
为了支持“查找以某词结尾的长词”，系统建立了一个反向索引：
- **Key**: 词语末尾 1 个字的韵律编码（末尾2字符，如 `v2`）。
- **Value**: 所有以此结尾的完整 Key 列表。

## 3. 查询算法流程

查询过程由 `queryDict` 函数主导，主要步骤如下：

### 3.1 输入标准化
使用 `pinyin-pro` 库获取用户输入的拼音，并进行标准化处理：
- **ü -> v**: 统一格式。
- **i 的分化**:
    - `i-flat`: 平舌音后 (z, c, s)
    - `i-retro`: 翘舌音后 (zh, ch, sh, r)
    - `i`: 其他声母后
    - *目的*: 避免“四(si)”与“十(shi)”在严格模式下被视为押韵。

### 3.2 变体键生成 (`generateQueryKeys`)
根据用户选择的**宽松度 (Looseness)**，生成所有可能的查询键。

| 等级 | 描述 | 逻辑 |
| :--- | :--- | :--- |
| **Tier 0** | 严格 | 仅生成完全匹配的 `韵母+声调`。 |
| **Tier 1** | 通押 | **合并相似韵母**，声调必须严格匹配。<br>例如 `an` 可匹配 `ang`, `ian`, `uan` 等（基于十三辙或合并组）。 |
| **Tier 2** | 谐音 | **合并相似韵母** + **忽略声调**。<br>系统会生成该韵母下 1-4 声的所有组合。 |

**韵母合并规则 (基于 `buildFinalVariants`):**
1.  **前/后鼻音互通**: `an/ang`, `en/eng/ong`, `in/ing`。
2.  **十三辙**: 使用传统十三辙分类（如“发花辙”包含 a, ia, ua）。

### 3.3 执行查询
1.  **精确长度匹配**:
    - 将生成的 Key 列表直接在 `globalDictData` 中查找。
    - 结果存入 `sameLength` 列表。

2.  **后缀匹配 (查长词)**:
    - 若输入长度 >= 2，取 Key 的末尾部分在 `suffixIndex` 中检索。
    - 找到包含当前 Key 作为后缀的更长 Key。
    - 结果存入 `moreLengths` 列表。
    - *优化*: Tier 2 模式下限制搜索数量以防卡顿。

3.  **降级匹配 (查短词)**:
    - 如果同长度查询无结果，且输入长度 > 2。
    - **递归策略**: 截取输入词的**末尾 n-1 个字**重新进行查询。
    - 例如: 查“奥特曼”(3字) 无果 -> 降级查“特曼”(2字)。

## 4. 匹配校验与过滤

查询得到候选词后，系统会进行二次校验 (`getPhraseMatchTier`)，确保准确性。

### 4.1 声母互斥规则 (Initial Mutual Exclusion)
为了保证押韵在听感上的自然度，系统在二次校验阶段 (`getPhraseMatchTier`) 引入了声母类型的过滤逻辑，防止具有强烈摩擦感的声母（平翘舌音）与普通声母混淆。

**1. 特殊声母组定义**
系统定义了一组“特殊声母”，涵盖了所有平舌音与翘舌音：
- **特殊声母**: `zh, ch, sh, r, z, c, s`

**2. 核心校验逻辑**
在逐字匹配过程中，系统会检查源词（用户输入）与候选词（词典匹配项）的声母属性：
- **规则**: 如果源词的声母**不属于**特殊声母组，而候选词的声母**属于**特殊声母组，则强制视为不匹配（返回 `-1`）。
- **逻辑表达**: `if (!srcIsSpecial && matchIsSpecial) return -1;`
- **目的**: 该规则主要用于保护“普通韵脚”的纯净度。例如，当用户查询“记忆 (ji yi)”时，系统会过滤掉“基石 (ji shi)”，因为“石 (shi)”的声母属于特殊组，会破坏整体的听感和谐。

**3. 与 i 韵隔离协议的协同**
此规则是系统 **Triple-I Isolation** 策略的重要补充：
- **严格模式**: `i` (普通)、`i-flat` (平舌)、`i-retro` (翘舌) 被视为独立韵母，通过韵母编码直接隔离。
- **宽松模式**: 当这些韵母被合并入“一七辙”时，声母互斥规则作为第二道防线，确保普通声母（如 `j, q, x`）不会意外匹配到摩擦感强的声母（如 `z, c, s`）。

**4. 局限性说明**
根据当前代码实现，该规则具有**单向性**：它限制了“普通词”匹配到“特殊词”，但允许“特殊词”在宽松模式下匹配到“普通词”（只要韵母在对应的通押范围内）。这在一定程度上扩大了平翘舌词汇的候选范围，同时保证了普通词汇的押韵质量。

### 4.2 平仄过滤
用户可选择过滤输出结果的平仄：
- **平声**: 1声, 2声
- **仄声**: 3声, 4声
- 过滤仅针对**尾字**的声调。

## 5. 特殊文件说明

- **`js/dict-worker.js`**: 负责在 Web Worker 中下载大文件并解析，避免阻塞 UI 线程。
- **`js/data.js`**: 包含本地兜底的小型字库和自定义字库逻辑。
